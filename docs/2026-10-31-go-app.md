# The Go app
**Date:** 2026-10-31

OrgView is now a Go program (`cmd/orgview`) that serves the same pages, reports,
treeviews and JSON endpoints as the Rails app, from the same SQLite database
(`storage/development.sqlite3` on the `orgview-jt-app-storage` volume). This is
phases 2 to 6 of the move to Go + SQLite; phase 1 (Rails on SQLite) is in
`2026-10-31-move-to-sqlite.md`.

The Rails app is still in the repo, unchanged, so it can run the one-time MySQL
copy and so the two can be compared on real data. It will be removed in a
follow-up once the Go app is verified.

## Running it

```sh
docker compose up -d --build app     # http://localhost:3001
```

Or without Docker (Go 1.25+):

```sh
make run      # serves storage/development.sqlite3 on :3001
make dev      # same, with live reload on http://localhost:3000
make test     # Go tests
make build    # bin/orgview
```

`orgview -addr :3001 -db path/to/file.sqlite3` (or `ORGVIEW_ADDR` /
`ORGVIEW_DB`). A missing database file is created with the full schema. An
existing database must have every Rails migration applied (run
`bin/rails db:migrate` once, as the MySQL copy steps do); the app refuses to
start otherwise.

Do the MySQL copy first if you haven't: the copy script refuses to run into a
database that already has data unless you pass `FORCE=1`.

### Live reload

`make dev` runs [Air](https://github.com/air-verse/air), which you install
once with `go install github.com/air-verse/air@latest`. It isn't a `go.mod`
tool, because that would pull Air's own dependencies (Hugo among them) into the
module and the Docker build's `go mod download`. On every change under `cmd/` or `internal/` it regenerates
the templ views, rebuilds and restarts the app; static files and `schema.sql`
count too, since they are embedded. Open http://localhost:3000, Air's proxy,
which reloads the browser after each rebuild. The app itself listens on :3002,
so the Docker container can keep running on :3001. If a build fails, the error
shows in the terminal and the last good build keeps serving. Settings are in
`.air.toml`.

The data lives in the Docker volume, so copy it out once first. Stop the
container so the copy includes everything still in SQLite's write-ahead log:

```sh
docker compose stop app
docker compose cp app:/app/storage/development.sqlite3 storage/
docker compose start app
```

That copy is separate from the container's: changes made under `make dev` stay
in `storage/` and don't reach the Docker app.

Writes through the proxy rely on the browser's `Sec-Fetch-Site` header (every
current browser sends it); a bare `curl -X POST` through :3000 is refused as
cross-origin, so point scripts at :3002 instead.

## Layout

| Path | What |
|------|------|
| `cmd/orgview` | the server binary |
| `internal/store` | SQLite access (`modernc.org/sqlite`, no cgo), schema, CSV importers, team stats |
| `internal/web` | handlers on the stdlib `http.ServeMux`, middleware, embedded static files |
| `internal/web/views` | [templ](https://templ.guide) templates; the generated `_templ.go` files are committed, run `make generate` after editing a `.templ` file |
| `cmd/parity` | the crawler used to compare every page against the Rails app |

Cross-site request protection uses Go 1.25's `http.CrossOriginProtection`
(Origin / Sec-Fetch-Site headers) instead of Rails' CSRF tokens.

## How parity was checked

`cmd/parity` crawled 477 URLs (every page, report, filter, sort, page number and
JSON endpoint reachable from the home page) against Rails and Go running on
copies of the same database. All 477 matched after normalising whitespace and
timestamps. Report rows that tie on a count come out in the order Ruby's
`sort_by` gives them; `internal/web/rubysort.go` ports Ruby 3.3's sort so the
order matches. The treeviews, charts, inline editing, move-team dialog and
version switcher were checked in a browser.

## Deliberate differences from Rails

These are fixes, not ports of the Rails behaviour:

- An employee's manager and direct reports are looked up within the same data
  version (Rails could cross versions).
- Deleting an employee or a data version's employees also removes their team
  memberships, instead of leaving orphan rows.
- Moving a team escapes `%` and `_` in team paths, so a team named with those
  characters doesn't drag unrelated teams along.
- CSV imports run in one transaction: a bad row leaves the data as it was.
- An import naming a `Team_ID` that doesn't exist shows an error instead of a
  500.
- Sort `direction` parameters are limited to `asc`/`desc`.
- The employee form's Save button submits the employee form (Rails' script
  picked the navbar's version-switch form).
- Flash messages show on the data version pages.
- Validation errors show on the employee form, and failed saves return 422.
- CSV uploads accept `application/csv` and `application/vnd.ms-excel` as well as
  `text/csv` (Excel on Windows sends the latter).
- Treeviews render names as text, not HTML.

## Not ported

- Rails' system tests (Capybara). The Go tests cover the same controllers and
  models through `httptest`.
